# v11.0.0 升级与发布指南

本页适用于从 v9/v10 升级的玩家，以及维护静态网页和 Cloudflare 联机服务的仓库拥有者。当前应用版本为 **11.0.0**，存档格式为 **11**，WebSocket 协议为 **11**。游戏前端和 Cloudflare Worker 是两个独立的发布目标；合并代码或更新网页不会自动更新原有 Worker。

源码、离线模型包、自动验证和部署配置都在本仓库中。下面描述可执行的升级步骤，不表示远端 CI、GitHub Pages 或你的生产 Worker 已完成本次发布。实际运行结果以对应提交的 Actions 记录、[验证记录](verification.md)和你自己的端点检查为准。

## 1. 先保存原来的英雄和部署配置

在**原游戏地址、原浏览器**打开存档面板，导出或复制 JSON 存档并保存为文件。v10 页面若只有复制 JSON 的入口，可将完整文本保存为 `.json` 文件；v11 另有“下载存档文件”。先核对英雄姓名、等级和主线进度，再关闭重复的游戏标签页。

本地浏览器存档属于完整来源，即协议、主机名和端口。以下是不同的存档空间：

- `http://127.0.0.1:8765/`
- `http://127.0.0.1:18865/`
- `http://localhost:8765/`
- 你的 HTTPS 线上游戏地址

换地址后出现新英雄，通常应先回到原地址查找并导出进度。JSON 是跨设备、跨端口迁移的入口。解压游戏文件不会把浏览器存档带到另一台电脑；浏览器中的恢复快照也不能替代下载到磁盘的副本。

维护联机服务时，另保存原来的 `cloudflare-worker/wrangler.toml`、Worker 名称、Durable Object 绑定和迁移历史、实际 WebSocket 地址以及使用的 `realm`。保留旧源码或发布包，便于定位版本差异。

## 2. 选择并下载交付包

打开 [Verify game and local AI](https://github.com/cjrujo/aethelgard-mud/actions/workflows/verify.yml)，选择打算使用的提交对应的运行，在 **Artifacts** 中选择：

| Artifact 名称 | 内含交付文件 | 适合谁 |
| --- | --- | --- |
| `aethelgard-source-game` | `aethelgard-v11.0.0-source.zip` | 直接游玩规则模式，或自行准备模型、开发、更新服务端 |
| `aethelgard-qwen-offline` | `aethelgard-v11.0.0-qwen-0.6b-offline.zip` | 希望一次取得游戏、真实 Qwen3 0.6B q8 权重及推理运行库，然后离线游玩 |

相应任务成功完成打包和上传后，artifact 才会出现。轻量包在游戏与工具任务中生成；完整离线包在模型文件准备和真实浏览器模型验证任务中生成。下载的 artifact 外层可能还包着一个 ZIP，先取出上述交付文件，再完整解压其中的 `aethelgard-mud` 文件夹。

**完整离线包包含实际模型文件，不只是下载器。** 轻量包和 GitHub 的 **Code → Download ZIP** 不含权重。模型默认是注册表固定 revision 的 Qwen3 0.6B **q8**，不可混入旧实验配置的 q4 文件；具体版本、文件和许可见 [模型注册表](../models/registry.json) 与 [AI DM 文档](ai-dm.md)。

没有现成 artifact 时，可在源码目录自行准备。构建和打包需要 Node.js 22.8+ 与 Python 3.10+；只运行已构建交付包只需 Python 和浏览器。

```bash
npm ci
npm run build
python tools/package_release.py
```

完整离线包另执行：

```bash
python tools/prepare_offline.py --model qwen-0.6b
python tools/prepare_offline.py --verify-only
python tools/package_release.py --model qwen-0.6b
```

输出位于 `dist-release/`。模型准备需要首次联网下载数百 MB；`--verify-only` 核对实际文件摘要，不联网、不修改文件。打包工具只产生本地 ZIP，不推送代码或部署服务。

## 3. 更新本地游戏并保留进度

1. 完成原地址的 JSON 导出，并停止旧启动器。将新包完整解压到一个新文件夹，保留旧包直到新版本与存档核对完成。
2. 在新目录双击 `start_Windows.cmd`，或在 macOS/Linux 运行 `sh start_unix.sh`；也可执行 `python tools/serve.py --open`。macOS/Linux 通常把命令中的 `python` 改为 `python3`。
3. 打开启动器实际打印的地址。首次优先使用端口 **8765**；占用或权限限制时，依次尝试 **18865–18874**，并在该目录记住成功的端口，以后优先使用它。新解压目录可能没有上次记住的端口。
4. 若仍是同一浏览器、同一地址，游戏会读取并迁移已有 v9/v10 存档。若地址改变，在新页面的“存档 / JSON”文本框粘贴原文件内容，点击“导入 JSON 存档”。核对英雄、装备、主线、故事选择与金币后再继续游玩。
5. 使用完整离线包时，打开“智脑”→“浏览器 CPU”→“Qwen3 0.6B”→勾选“使用已下载的离线模型包”→“加载离线模型”，等实际就绪后提问。

如果旧端口仍可使用，也可以显式指定它，例如：

```bash
python tools/serve.py --port 8765 --open
```

显式 `--port` 要求使用该端口，失败时会报错，不自动回退。无论使用哪个端口，都应保持启动器终端开启。通过 `file://` 双击 HTML 不能代替本地 HTTP 服务。

完整离线包复制后可先运行 `python tools/prepare_offline.py --verify-only`。轻量包用户若希望离线运行模型，应先执行准备命令。只依赖浏览器曾经下载过模型，不等于模型文件仍完整保留；可复制的完整离线包与浏览器缓存是两种不同方式。

## 4. 更新线上静态前端

从同一份 v11 源码执行 `npm ci`、`npm run build`。构建会同时生成前端和 Worker 的构建信息。手动部署静态站点时，保留下列相对路径并一起上传：

```text
index.html
open_world_mud.html
sw.js
build-info.json
assets/game.css
assets/ai-worker.js
models/registry.json
```

这对应仓库 Pages 工作流发布的游戏壳。源码中的 HTML 由模块生成，修改 `src/` 后要重建；只替换一个 HTML 会留下旧样式、推理 Worker 或版本信息。默认静态站点不包含大模型权重，浏览器在线模式会按注册表加载；本地完整离线包则从自己的 `models/` 和 `vendor/` 读取文件。若自行托管离线模型，应按 [AI 离线文件说明](ai-dm.md#方式-b提前下载完整文件包) 一并提供对应目录和清单。

### 使用 GitHub Pages 工作流

正常自动流程为：`main` 的 **Verify game and local AI** 成功 → Pages 工作流取同一提交 → 构建与验证 → 发布静态前端。手动触发 Pages 工作流也先构建和验证选定提交。

工作流先检查仓库现有 Pages 配置。如果尚未启用 Pages，或发布来源不是 GitHub Actions，发布任务跳过，并在运行摘要说明原因。它不会自动修改仓库设置。若确实希望在 Pages 发布前端，再由仓库维护者在 **Settings → Pages** 选择 GitHub Actions。**无需启用 Pages 也可以运行验证和下载 Verify 任务生成的交付包。**

Pages 是一种静态托管方式。已经使用其他静态托管服务的项目可继续使用原服务；Cloudflare Worker 联机后端仍需按下一节独立更新。

### 让已打开的页面载入新构建

v11 页面检测到新的 `build-info.json` 后显示“保存并更新”。点击后先保存英雄，再准备和激活新 Service Worker；离线壳尚未就绪时会提示稍后再次点击。保存失败不会直接刷新丢掉当前页面，在线战斗中需先结束对局。

首次从 v10 升级时，旧页面可能没有这个入口。先导出 JSON，再刷新或重新打开原地址，随后在“连接与版本诊断”核对前端版本。如果仍显示旧版，先检查托管服务是否确实提供新的 `build-info.json`、HTML 和 `sw.js`，再处理旧页面缓存；不要把清空浏览器存档作为升级步骤。

## 5. 更新现有 Cloudflare Worker

**v11 前端使用协议 11，原 v10 Worker 需要同步更新。** 浏览器中负责本地推理的 Web Worker 与 Cloudflare 联机 Worker 是不同组件；下载模型或更新游戏网页都不会替换云端服务。

先保留部署到原服务所需的配置，再以 v11 的完整模块部署：

| 文件 | 更新要求 |
| --- | --- |
| `cloudflare-worker/entry.js` | v11 运行入口，仅导出 Worker handler 和 Durable Object 类；Wrangler 的 `main` 必须指向它 |
| `cloudflare-worker/worker.js` | 使用 v11 的协议、会话与服务器战斗实现 |
| `cloudflare-worker/receipts.js` | 一并部署；持久保存尚未确认的战斗奖励 |
| `cloudflare-worker/build-info.js` | 使用本次构建生成的文件，与前端 `build-info.json` 对应 |
| `cloudflare-worker/wrangler.toml` | 设置 `main = "entry.js"`；核对原 Worker 名称、`AETHELGARD_REALM` 绑定、`AethelgardRealmDO` 类名及既有迁移历史，保留原环境的配置 |

现有 `v1` SQLite 类迁移保留不动，奖励账本首次使用时创建；更新无需删除 Durable Object 数据库或重建领域。继续使用原 Worker 名称和 `realm`，才能继续连接同一服务与领域。

在仓库根目录构建，再进入 Worker 目录部署：

```bash
npm ci
npm run build
cd cloudflare-worker
npx wrangler@4.152.0 deploy
```

尚未登录 Wrangler 时，部署前执行 `npx wrangler@4.152.0 login`；这个固定版本与本轮本地运行时验证一致，需要 Node.js 22 或更新版本。只在 Cloudflare 网页编辑器粘贴 `worker.js` 会缺少其导入的模块；使用完整目录和 Wrangler 部署。详细配置和允许的网页来源见 [联机部署说明](online.md#更新或部署-cloudflare-领域)。

发布后打开实际服务的健康检查地址，例如：

```text
https://YOUR-WORKER.YOUR-SUBDOMAIN.workers.dev/health?realm=friends
```

确认响应中 `protocol` 是 `11`，`build.version` 是 `11.0.0`，`build.id` 与本次前端构建对应。浏览器联机地址使用相同服务和领域，例如：

```text
wss://YOUR-WORKER.YOUR-SUBDOMAIN.workers.dev/websocket?realm=friends
```

打开游戏的“连接与版本诊断”，核对前端版本、服务端版本、协议与连接状态。收到匹配的完整握手后才算连接成功，只有 WebSocket 打开还不够。“复制诊断信息”不包含恢复 token，可用于排查版本或连接问题。

如果设置了 `ALLOWED_ORIGINS`，允许来源需要包含实际前端的完整 Origin。本地启动器换了端口时，要按实际地址更新允许来源；`localhost` 与 `127.0.0.1` 不能互相替代。配置例子见 [联机文档](online.md)。

## 6. 升级后有哪些行为变化

| 变化 | 玩家会看到的行为 |
| --- | --- |
| 关键剧情进入默认路线 | “目标下一步”穿过各章故事与准备，再指向首领。“暂缓此线索”只改变推荐，日志可回访。旧版已完成主线从现有进度继续，不强迫补做序章。 |
| 终章可以补线索 | 最终选择显示结局条件和未完成线索。此前已做的选择仍保留后果；最终首领进度完成后，守护归路结局始终可选。 |
| 高阶资源需要准备 | 以太水晶、秘银/火绒花、星辰金属需要相应章节完成，或在公会达到等级、声望并购买训练。自由移动保留；不满足条件不会白扣采集体力。 |
| 公会有实际成长入口 | “公会与伙伴”显示普通声望等级、折扣、套装/部位定向兑换和伙伴培养。训练与兑换需要到公会大厅，价格在付款前可见；碎片真实消耗。普通声望与五阵营信任分别计算。 |
| 伙伴与姿态一致 | 伙伴显示真实培养等级，所有已解锁伙伴共享培养成长；防御姿态同时降低物理和魔法进攻能力，换取防御提升。 |
| 自动狩猎有终点 | 默认完成一场胜利即停；可按当前击杀契约停止，或主动选择连续模式。连续模式先给出五场上限，填 `0` 才代表不限场数；可设生命下限。界面保留本轮战斗收益和停止原因。 |
| 安全暂停仍保留 | 低生命且不足撤退体力时停止自动行动，当前战斗交还手动。重载不自动恢复狩猎；自动策略不会悄悄消耗药剂。 |
| 战斗与智脑使用同一效果 | 打断蓄力使存活敌人下一回合露出破绽；打断施法只取消当前法术。建议读取真实资源、冷却和行动效果。 |
| 智脑有长期声明与继续入口 | 明确的人物姓名、承诺独立于短聊天窗口保存；“重新加载并继续”恢复保留的问题，继续前核对场景。反馈可在本机记录并导出。 |
| 联机开始前锁定，奖励可恢复 | 加入/排队请求发出前暂停单人活动；断线结束进行中的战斗。服务器已结算的未确认奖励，可由同一英雄重连同一服务与领域恢复。 |

具体门槛、价格和取舍见 [玩法设计](gameplay-design.md) 与 [战斗与经济审计](combat-audit.md)。AI 的长期记录只提取有限明确句式，不代表模型能正确记住任何聊天，也不代表承诺已经履行。真实 0.6B 模型仍会编造 NPC 关系的原因；规则事实卡和本机反馈有助于发现问题，不能消除所有幻觉。参见 [AI 内容验收](ai-dm.md#当前模型的实测范围与限制)。

## 7. 多标签、恢复快照与导入失败

同一来源下的英雄只有一个页面能写入。第二个标签页会显示只读提示，可以“接管并载入最新进度”。接管需要原页面先保存成功；若保存失败，原页面保留写入权，提示先导出，接管不会把未保存的成果替换成旧存档。成功接管后的页面载入最新存档，原页面暂停后台活动。浏览器支持时使用 Web Locks；其他环境采用协作释放租约和存档冲突检查。

若发生页面冲突，可以先“导出本页进度”，再决定是否接管。不要把两个标签页里不同的旧状态当作可以自动合并的两份进度。单人和在线玩法、智脑对话与反馈都遵守当前页面的写入权。

在“存档 / JSON”→“恢复快照”中，可以选择上一位英雄、恢复前快照、冲突页面快照或保留的原始异常数据，下载后检查。可校验的快照可以恢复；无法解析的原始数据仍可下载，但不能直接作为有效英雄载入。

新旅程、导入和恢复会先核对备份是否写入成功。备份失败时保留当前英雄；新状态保存失败时恢复原英雄，并显示失败原因。浏览器空间不足时，优先把当前 JSON 和需要保留的快照下载到磁盘，再处理存储问题。清空全部站点数据会同时删除该来源下的存档和快照。

## 8. 发布后的核对与回退

先确认版本，再检查实际玩法，避免只凭“页面能打开”判断升级完成：

1. 前端诊断显示 `11.0.0`；有联机时，`/health` 显示协议 `11`，前后端构建 ID 对应。
2. 原英雄的等级、金币、装备、章节和已选故事保留。新标签页先显示只读，接管后能载入最新进度。
3. “你的旅程”可进入故事、日志、公会与狩猎设置；单场狩猎结束后可看到成果和停止原因。
4. 本地模型加载完成后产生带真实模型来源的回复；打开规则事实卡比较当前状态，取消请求后能看到继续入口。规则助手回复不算模型验收。
5. 有联机部署时，用两台设备确认握手、同房间聊天、完整协作或决斗，以及已完成奖励的断线恢复；三对三另需六位已连接英雄。

开发验证命令可单独运行：

```bash
python tests/verify_mud.py --report test-results/verification.json
npx playwright install chromium
node tests/browser.mjs --report test-results/browser.json
node tests/browser-update.mjs
```

已准备真实模型后，再运行：

```bash
node tests/browser.mjs --model --report test-results/browser-model.json
npm run test:model -- --model=qwen-0.6b --local
```

逻辑回归、真实浏览器界面、实际模型推理、模型内容质量和公网部署是不同检查。这些命令本身不是通过记录；最终结果与覆盖限制应保留在对应报告中。完整文件包在外网请求被阻断时的模型测试，也不等于所有浏览器缓存都能断网重载。

需要回退时，先导出当前 v11 进度并保留它，再恢复匹配的旧前端和旧 Worker。旧版本未承诺能够理解所有 v11 字段，应使用升级前导出的存档进行回退核对。保留原 Worker/DO/realm 配置和数据，不以删除领域数据库作为回退办法。
