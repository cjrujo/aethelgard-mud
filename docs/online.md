# 联机：真实会话、协作副本与可恢复结算

v11 客户端为 [`src/online.js`](../src/online.js)，服务器实现为 [`cloudflare-worker/worker.js`](../cloudflare-worker/worker.js)，部署入口为 [`cloudflare-worker/entry.js`](../cloudflare-worker/entry.js)，持久奖励收据由 [`cloudflare-worker/receipts.js`](../cloudflare-worker/receipts.js) 管理。前后端使用 **WebSocket 协议 11**。本仓库包含本地协议、故障恢复、客户端集成及真实 workerd 冒烟测试；这些测试不代表已部署你的 Cloudflare 端点，也不能代替两台设备的公网验收。

## 玩家使用

打开联机面板，填写联机昵称、队伍标记与服务地址。昵称独立于离线英雄姓名；队伍标记是展示文本，不是账户或公会认证。

| 服务地址 | 连接范围 | 功能 |
| --- | --- | --- |
| 留空 | 同一浏览器、同一来源的其他标签页，使用 BroadcastChannel | 在线名单、同地点聊天 |
| 已部署的 `wss://…` v11 端点 | 同一服务器领域中的实际 WebSocket 连接 | 在线名单、同地点聊天、2–4 人协作副本、1v1、3v3、待领取结算恢复 |

同源要求协议、域名和端口一致，`localhost` 与 `127.0.0.1` 也属于不同来源。一个英雄的存档同时只有一个标签页可以写入；只读标签页需先“接管并载入最新进度”才能加入在线对局。标签页模式不连接其他电脑、不生成队友、不提供协作或竞技奖励。

连接真实领域前，客户端先为英雄生成并保存恢复身份。收到服务器 `welcome`、发送角色快照和恢复身份、收到匹配的 `ready` 后才显示连接成功。仅打开 WebSocket 不算就绪。HTTPS 页面要求 `wss://`。连接失败、协议不符或握手超时会显示具体原因。

### 加入、等待与退出

点击加入副本或匹配时，界面立即显示“正在加入”，同时暂停自动狩猎和自动行走，并锁定相关单人行动。无需等待服务器回包才生效，因此网络延迟不会让角色同时开打单人战斗。

- 服务器接受后，显示副本人数或匹配进度，例如 `1/2`、`3/6`。
- 服务器明确拒绝后，解除本次请求的等待状态；已有队伍或对局仍按原状态处理。
- 请求超过 12 秒没有确认，客户端会断开连接，取消该连接可能仍在服务器排队的状态；迟到回包不会重新锁住角色。
- 等待回包时可以“取消并断开”；已进入队列可退出匹配；队伍中可以离开。
- 离开或断线按离场处理；进行中的战斗不会重连恢复。**已经持久记录的结算可以补领。**

同一份英雄存档从另一个窗口连接同一领域时，服务器替换旧会话，旧窗口会收到说明。不能靠复制同一个恢复身份在同一领域占据两个队伍位置；这也不是对独立自然人的身份认证。

### 协作副本

1. 至少两名玩家连接同一领域，在游戏中移动到同一地点。
2. 各自点击协作副本，进入同一个最多四人的队伍。首位加入者为队长。
3. 队长在人齐后开始。加入、等待和开始都不发奖。
4. 每回合查看首领意图，选择攻击、职业技能、防御或自我治疗。技能有冷却，每人每场有两次治疗。
5. 全部存活参与者提交行动，或达到 20 秒时限后，服务器结算回合；超时者自动防御。

首领有集中攻击、横扫、恢复三种意图，低血量时进入狂暴阶段。血量、伤害、冷却、治疗次数和贡献由服务器计算。战斗使用单独的入场血量与属性快照，期间不能通过同步离线装备改变入场属性。

胜利奖励发给结算时仍连接且至少主动提交过一次有效行动的参与者。全程超时自动防御不算贡献；此前作出贡献、仍在会话中的倒下队员可以共享胜利。失败、平局、加入和离开不产生收益。结算开始后显示“正在保存战斗结算”，持久写入成功后才显示结束并投递奖励。

### 竞技场

1v1 需要两位已连接英雄；3v3 必须等到六位，不用机器人补齐。队列分开，重复点击不会增加自己的匹配人数，队伍由服务器分配。

竞技场使用按职业固定的入场属性，保留各职业的技能、防御与治疗选择。双方回合攻击统一结算；不能攻击队友、重复提交同一回合或重放旧回合。30 回合后仍未分出胜负则判平。排队没有奖励，未参与便因对方弃权取胜也不发奖。

## 奖励如何恢复

v11 把“战斗结束”“奖励存入英雄”“服务器收到领取确认”分开处理：

1. **服务器先保存。** 将参与者的结算写入该领域 Durable Object 的同一个存储事务。事务失败时不发送奖励，维持结算中状态并重试。
2. **客户端验证归属。** 检查当前会话、英雄、奖励账本、序号和数值；旧会话或其他英雄的消息不能给当前角色加奖励。
3. **客户端保存英雄。** 奖励、升级、装备与去重记录一起保存。本地写入失败会回滚本次内存中的奖励及生成内容，不发送领取确认；服务器保留待领收据。只读标签页也不领取。
4. **确认后删除待领记录。** 客户端成功保存后发送 `receipt_ack`，服务器持久确认后移除该收据。同一确认可以重复发送。

最终结算消息发送失败、客户端刷新、确认回执丢失或服务器实例重建后，用**同一英雄存档、同一服务和同一 realm**重新连接即可补领。客户端以账本和递增序号去重，已保存但未确认的奖励会重新确认，不再发一次金币或装备。乱序收据也不会跳过较早的未领结果。

联机面板的“战斗奖励”显示待领状态，也提供“领取待收奖励”。恢复时每批最多 16 份；仍有待领结果时定期继续检查。每个英雄在一个领域最多保留 128 份未确认结算，达到上限后需先领取再加入新对局。

### 恢复身份与存档的边界

恢复身份包含随机英雄 ID 与浏览器密码学随机生成的 256 位 token。token 随英雄 JSON 存档保存，并按服务来源和 realm 隔离。服务器通过 token 的 SHA-256 摘要查找绑定的英雄记录，不把原始 token 写入持久账本、在线名单、聊天、战斗快照或诊断信息。

- 新旅程生成新的恢复身份，不能领取上一位英雄的奖励。
- 恢复或导入原英雄的完整 JSON 会保留其恢复身份，因而可以领取该英雄尚未确认的结果。
- `v10` 的昵称、荣耀和旧奖励 ID 会迁移；首次连接 v11 时才创建并保存新恢复身份。v10 时代没有持久收据，无法补发那时已经丢失的结果。
- JSON 存档包含恢复凭证，应当作为自己的游戏存档保管。持有完整复制品的人能够以该英雄连接；这不是账户认证或完整反作弊。
- 收据只恢复未确认的战斗结算，**不备份整个人物**。导入一个很早的旧 JSON，可能回退此前已经确认、也已经写入较新本地存档的进度；服务器不会再次发放这些已确认奖励。
- 未进入持久结算的进行中战斗仍在内存里，服务器重启会终止它。若持久存储故障持续到实例被终止，尚未写入的结果不能保证恢复；界面不会把它显示成已安全保存。

## 更新或部署 Cloudflare 领域

已有 v10 服务器需要同步更新为 v11；静态游戏页面和 Cloudflare Worker 是两次不同的发布。保持原 Worker 名称、Durable Object 绑定、类名与领域参数即可继续使用原服务地址。现有 `v1` SQLite 类迁移保留不动，奖励账本在首次使用时创建，不需删除领域数据库。

先在仓库根目录构建，使前端和服务器拥有同一次生成的构建 ID，再部署服务器：

```bash
npm ci
npm run build
cd cloudflare-worker
npx wrangler@4.152.0 deploy
```

第一次使用 Wrangler 且尚未登录时，在部署前执行 `npx wrangler@4.152.0 login`；该固定版本与本轮真实运行时验证一致，需要 Node.js 22 或更新版本。本地源码包含多个模块：`entry.js`、`worker.js`、`receipts.js` 和生成的 `build-info.js`，应通过仓库构建和 Wrangler 一起上传。保留 `wrangler.toml` 中的 `main = "entry.js"`：该入口只导出平台允许的处理器和 Durable Object 类，业务模块里的协议常量与测试函数不会被错误当作 Worker 入口。只在控制台粘贴 `worker.js` 会缺少模块并可能被无效入口导出阻断启动。

部署完成后将实际地址的 `https://` 改为 `wss://`，填入联机面板，例如：

```text
wss://YOUR-WORKER.YOUR-SUBDOMAIN.workers.dev/websocket?realm=friends
```

`realm` 由 1–48 个字母、数字、下划线或连字符组成，省略时为 `global-shard-1`。不同 realm 的名单、队列、战斗和奖励账本隔离。服务器接受 `/`、`/websocket`、`/health` 的 GET 请求，普通 HTTP 返回协议、构建信息和当前会话统计。

打开下列地址核对实际发布版本：

```text
https://YOUR-WORKER.YOUR-SUBDOMAIN.workers.dev/health?realm=friends
```

返回数据中的 `protocol` 应为 `11`，`build.version` 与 `build.id` 应对应这次构建。再刷新游戏，打开“连接与版本诊断”核对前端版本、服务器版本、协议、连接状态和最近通信时间。“复制诊断信息”不包含恢复 token；无法调用剪贴板时会显示可手动复制的文本框。

旧 v10 页面无法协商协议 11，可能仍显示其代码中固化的“服务器需要 v10”错误。需要同时更新静态页面并刷新前端缓存，以 `/health` 的实际协议和 v11 诊断面板核对两端版本。v11 页面连接尚未升级的 v10 服务器时会明确提示升级服务器。

如需限制允许连接的网页来源，在 `wrangler.toml` 增加：

```toml
[vars]
ALLOWED_ORIGINS = "https://YOUR-SITE.example,http://127.0.0.1:8765"
```

这里按完整 Origin 精确匹配；本地启动器使用了其他端口时应改成实际端口。逗号可分隔多个来源。未配置则不检查网页来源白名单；该检查也不是玩家身份认证。

部署后用两台设备核对握手、同房间聊天、完整副本、决斗、断线后已完成奖励的恢复和重复确认处理。3v3 需要六位已连接英雄。上述命令是部署步骤，不表示本仓库的测试已经替你执行公网发布。

## 协议摘要

所有数据包为 JSON。服务器生成 session ID 并绑定 WebSocket，不采用客户端传来的演员 ID 执行其他人的行动。

| 阶段 | 客户端请求 | 服务器消息 |
| --- | --- | --- |
| 握手 | `hello`：协议 11、角色快照、英雄 ID、恢复 token | `welcome`、匹配会话的 `ready`，含构建与收据摘要 |
| 在线与位置 | `ping`、`sync` | `pong`、`synced`、`presence` |
| 聊天 | `chat` | 服务器附加实际发送者和房间的 `chat` |
| 加入与离开 | `raid_join`、`raid_start`、`arena_queue`、`queue_leave`、`battle_leave`，带 `requestId` | `queue`、`queue_left`、`battle`、`battle_left`；请求错误原样返回 `requestId` |
| 回合 | `battle_action`，含战斗 ID、回合号、行动与目标 | 更新的 `battle` 快照 |
| 持久结算 | 无需单独请求当前战斗结算 | `battle` 依次进入 `settling`、`finished`，然后投递 `battle_result` |
| 补领与确认 | `receipt_sync`、`receipt_ack` | `receipts_status`、一批 `battle_result`、`receipt_acked` |

`battle_result` 包含当前投递会话 ID、英雄 ID、账本 ID、递增序号、稳定 reward ID、战斗 ID、结果及有界奖励。补领时会话 ID 改为新连接，reward ID 保持不变。客户端即使没有保留旧战斗面板，也能验证当前恢复身份并处理持久收据。

服务器对同一领域的消息、离场与定时回合按顺序处理；奖励记录使用 Durable Object Storage 的 `transaction()`。所用异步 KV 接口与事务可用于本仓库的 SQLite Durable Object 类，平台语义见 [Cloudflare SQLite Storage 文档](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/#transaction)。

## 当前服务边界

- 一个领域最多 100 个连接；只接受三个已知职业，角色快照的属性有有限值检查和上限。竞技场按职业统一属性，离线人物仍由玩家持有。
- 单包最多 8,192 个字符，每个会话每 10 秒最多 45 条消息。聊天最多 240 字符，间隔至少 800 毫秒。收据分批投递，避免补领时一次产生大量确认消息。
- 握手等待约 15 秒清理，静默会话约 90 秒清理，副本大厅约 120 秒过期，匹配队列约 180 秒过期。周期检查可能带来数秒差异。
- 当前没有账户、可信排行榜或完整反作弊。不同 token 仍可能由同一人持有；昵称和队伍标记可自行填写。
- 采用原生 WebSocket `accept()`，实时队列和进行中的战斗不做休眠或重启恢复。已持久写入的收据保存在该领域的数据库中。
- 接入的是玩家填写的服务器。客户端验证减少错误与跨会话污染，不是对恶意服务器的独立权威证明。

## 本地验证

```bash
node --test --experimental-test-isolation=none tests/online.test.mjs tests/online-reliability.test.mjs
```

测试运行实际客户端和 Worker 业务逻辑，仅用受控 DOM、WebSocket、时钟和事务存储替身隔离环境。覆盖正常聊天／组队／战斗、等待回包锁定、超时和迟到消息、存储失败回滚、结果发送失败、确认丢失、实例重建、跨英雄／跨会话拒绝、恢复 token 不泄露、乱序去重、分批补领及版本诊断。

测试中的“服务器实例重建”指重新实例化真实 Worker 类并复用模拟持久数据库；不等于已经验证 Cloudflare 的公网网络或生产存储故障。运行结果以本次实际测试输出和 [验证记录](verification.md) 为准。

### 真实本地 Worker 与 SQLite 恢复

`tests/worker-smoke.mjs` 通过实际 HTTP/WebSocket 连接本地 workerd，只允许 loopback 地址，使用新建的合成英雄。它不需要 Cloudflare 账户。Node.js 22 或更新版本内置的 WebSocket 即可运行；Wrangler 不作为游戏运行依赖安装。

完成仓库构建后，在第一个终端启动固定版本的本地 Worker：

```bash
npx --yes wrangler@4.152.0 dev --local --config cloudflare-worker/wrangler.toml --ip 127.0.0.1 --port 8787 --persist-to /tmp/aethelgard-worker-smoke-data
```

另一个终端运行：

```bash
node tests/worker-smoke.mjs --url http://127.0.0.1:8787 --phase seed --state /tmp/aethelgard-worker-smoke.json
```

`seed` 检查健康状态、构建与旧协议提示，完成真实 15 回合决斗，故意不确认胜利收据，并把合成身份写入临时文件。停止第一个终端的 Wrangler，然后使用**同一条启动命令和同一存储目录**重新启动，再运行：

```bash
node tests/worker-smoke.mjs --url http://127.0.0.1:8787 --phase recover --state /tmp/aethelgard-worker-smoke.json
```

`recover` 检查重启后的收据 ID、账本、序号与奖励均保持不变，投递使用新会话；发送两次确认，重新连接后验证待领数为零。成功后删除合成身份文件。只需检查连接内的发奖／补领时，可使用默认 `--phase all`；验证跨进程重启必须执行上述两阶段。Windows 可把 `/tmp/…` 换为本机临时目录，两次启动保持路径相同。

本次修改已按两阶段流程通过 Wrangler 4.152.0 的本地 workerd 与 SQLite 验证。生产网络、Cloudflare 账户配置以及公网部署仍需按实际服务环境验收。

在 Linux／macOS 和 CI 中，可用自动包装器执行上述整个流程。先把固定版本 Wrangler 安装到一个临时目录，再将 `WRANGLER_CLI` 设置为该安装下 CLI 文件的**绝对路径**：

```bash
WRANGLER_CLI=/absolute/path/node_modules/wrangler/wrangler-dist/cli.js node tests/worker-runtime.mjs
```

包装器校验版本为 `4.152.0`，选择随机本机端口，创建临时持久目录，执行完整决斗、停止整个运行时进程组、重新启动和补领验证，并在结束时清理进程及临时数据。结果写入 `test-results/worker-runtime.json`，仅含构建、检查项、结果和时长，不含恢复凭证。它不安装依赖、不登录或部署服务器。Windows 可使用前述手动两阶段命令。
